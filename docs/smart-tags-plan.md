# 智能匹配标签（Smart Tag Matching）功能规划

> 状态：**规划中**（2026-09-15 重新构想，取代已回退的 P1「自动打标」）
> 关联文档：ROADMAP.md（已同步指向本文件）

---

## 1. 目标与范围（本次重构的核心约束）

- **不独立成页 / 不成独立功能模块**。它出现在「多选收藏后出现的工具条」里，与「批量更改标签」**并列**作为一个按钮。「批量更改标签」本身 = 批量打标签 + 批量删除共同标签 合二为一。
- **只做检索，不新建标签**。从用户**已有的标签库**里，检索哪些标签能匹配选中内容的「来源处文本」，把候选标签提给用户，由用户选择性应用。
- **不做**学习、不做签名库、不做自动应用、不做 `auto_assigned` 列 / 撤销机制。纯前端关键字检索。

### 与已回退 P1「自动打标」的本质区别

| 维度 | 已回退 P1（自动打标） | 本次规划（智能匹配标签） |
|------|----------------------|--------------------------|
| 落位 | 独立页面 / 单独入口 | 多选工具条按钮，与「批量打标签」并列 |
| 标签来源 | 从手动标签学习关键词签名 | 直接匹配已有标签名 |
| 新建标签 | 会（建议新标签） | **绝不**，只复用已有标签 |
| 数据库 | 需 `item_tags.auto_assigned` 列 + 撤销 | **零 schema 改动，无迁移** |
| 后端 | 多条命令 + 签名构建 | 无（复用 `update_item_tags`） |
| 复杂度 | 高 | 低，纯前端 |

## 2. 交互与落位

**已确定方案**：多选工具条（`LibraryPage` 的 `selection-toolbar`）中，「批量更改标签」与「智能标签」**并列**为两个独立按钮：

```
[ 批量更改标签（N）] [ 智能标签（N）] [ 导出（N）] [ 删除选中（N）]
```

- 「批量更改标签（N）」打开 `BatchTagEditorModal`：上半部分「添加标签」（检索已有标签 + 空格新建），下半部分「批量删除标签（共同标签）」（勾选共有标签后移除）。
- 「智能标签（N）」打开 `SmartTagModal`（沿用 `BatchTagEditorModal` 的弹窗骨架与 `TagBadge` 勾选 chip 样式）。

`SmartTagModal` 弹窗内容（**按内容视角**）：
1. 对选中的 N 条收藏，逐条扫描来源文本，匹配已有标签库，记录「在哪个字段、哪段文字命中」的溯源。
2. **逐条内容**展开：每条收藏下列出它匹配到的标签，每个标签带命中字段 + 高亮片段，默认全勾选（即默认都打），不想要的取消勾选。
3. 每条内容右侧「确认（N）」只给这一条打上勾选的标签；无匹配标签的项显示「无匹配标签」、无确认按钮。
4. 确认后弹窗不自动关闭，列表刷新后候选自动重算（已挂载的标签会掉落），便于逐条连续处理。

> 历史决策：曾尝试把智能匹配作为 `BatchTagEditorModal` 内的一个 section（与「批量删除标签」并列），后按用户要求**拆分独立**。独立按钮交互更聚焦、职责更清晰，故以独立弹窗为准。

## 3. 匹配算法

**来源文本（v1）=** `title` + `description` + `authorName` + `partitionName` + `source`
（不含 `notes`——批注是用户自己写的，不是「来源处文本」；如需可后续作为可选增强。）

**标签候选键** = 标签的 `name`（归一化小写）。v1 不做每标签的别名/关键词扩展。

**关键优化（避免 S×T 朴素子串爆炸）**：
- 一次性构建**一个**大小写不敏感的正则，把全部标签名用 `|` 连接：
  `new RegExp(tagKeys.map(escapeRegex).join('|'), 'gi')`
- 每条收藏的来源文本**只扫一遍**该正则，记录命中的标签 id 集合。
- 命中后按 `tag.id` 去重，并剔除该 item 已挂载的标签（幂等，不重复添加）。

**质量旋钮**：ASCII 标签名加词边界 `\b`（避免 `go` 误中 `google`）；CJK 标签名用子串（无词边界）。
实现：`/^[A-Za-z0-9]+$/.test(name) ? \b${esc}\b : ${esc}`。

## 4. 数据流（纯前端，无后端改动）

- 输入已在 `LibraryPage` 内存中：`items`（每条带 `title/description/author/partition/source` 及已有 `tags`）、`tags`（完整标签池）。
- 全程同步、内存计算，**无 DB 读取、无网络、无异步**。
- 应用打标复用现有 `api.updateItemTags(itemId, mergedTags)`（底层 `replace_item_tags` 整表替换），无需新增 Rust 命令。

## 5. 性能评估（V8 实测）

> 运行环境是 WebView2 的 **V8**（Irregexp 引擎），不是 CPython 的 `re`。
> ⚠️ 注意：Python `re` 对「上千候选的交替正则」有严重回溯，在我的基准里跑到 2–8 秒量级，**完全不具代表性**；以下数字用 **Node 22（同 V8 引擎）** 实测，单正则扫描整批选中项的耗时。

**基准模型**：每条文本都把全部标签词嵌进去（最坏情况：每条都命中所有标签），测量「构建正则 + 扫描全批」的耗时。

| 场景 | 选中条数 S | 标签数 T | 平均文本长度 L | 单正则扫描耗时 (V8) |
|------|-----------|---------|---------------|---------------------|
| 当前真实规模 | 50 | 38 | 200 | **0.06 ms** |
| 较重 | 200 | 200 | 500 | **1.48 ms** |
| 重度 | 1000 | 500 | 800 | **21 ms** |
| 极端 | 1000 | 1000 | 1000 | **44 ms** |
| 压力（远超个人库上限） | 3000 | 2000 | 800 | 296 ms |

**结论**：
- 真实场景 + 常见重度选择（≤200 条 / ≤200 标签）均在 **1 帧（16ms）** 内，毫无感知。
- 即便「1000 条 / 1000 标签」这种极端批量，也仅 **44ms**，是一次操作可接受的范畴，不会卡 UI。
- 只有「3000 条 × 2000 标签」这种**远超个人收藏库体量**（当前 208 条 / 38 标签）的压力用例才破 100ms；属一次性操作，若仍担心可放进 `requestIdleCallback` 或 Web Worker，**v1 不必**。
- 单正则扫描把朴素 S×T 的子串比较降为约 **S×L 的线性扫描**，是性能可控的根本原因。

**应用（apply）耗时**：
- 候选确定后，对每条命中 item 计算「原标签 ∪ {新标签}」再调 `updateItemTags`，每条一次 Tauri 异步往返。
- 按项目经验自动提交约 2.3ms/行：S=50 每条加 1 标签 ≈ 50 次调用 ≈ **<150ms**，体感顺滑。
- 若批量极大，建议后续加一个批量命令 `apply_smart_tags(assignments: [{itemId, tagIds}])`，单事务落库（复用 `replace_item_tags`），符合「批量写必须收进一个事务」原则。**v1 先复用 `updateItemTags` 逐条即可。**

## 6. 边界与质量

- **标签库为空** → 提示「标签库为空，请先创建标签」。
- **选中项来源文本都无命中** → 提示「未从来源文本中匹配到可添加的标签」。
- **候选去重后为空**（命中的标签 item 都已挂载）→ 同上提示，不展示空列表。
- **大小写**：匹配双方统一归一化为小写。
- **命名空间**：v1 匹配全部命名空间（`manual` / `system` / `auto`）的已有标签；把 `auto` 标签再提议回去也合理。
- **部分命中**：某候选可能只命中选中项中的一部分；UI 显示覆盖率，由用户决定是否应用，应用只落到命中子集、不强制全选。
